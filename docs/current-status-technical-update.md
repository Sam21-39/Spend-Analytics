## 1. Executive Summary

Spend Analytics is currently a Flutter mobile application focused on offline-first personal finance tracking. The codebase has a mature local-first foundation: Drift is the source of truth for most reads, GetX manages routing/state/dependency lookup, Supabase provides optional authentication/cloud sync/realtime, and Firebase is used for analytics and crash reporting when configured.

The strongest implemented areas are transaction capture, dashboard summaries, analytics, category-aware budgets, local notifications from rules, voice-to-transaction capture, settings/preferences, guest mode, Google/Supabase sign-in, and the shared Liquid Glass design system.

The main unfinished or partially aligned areas are recurring expenses, richer rule evaluation, subscription monetization, category cloud sync, payment-mode parity between local and Supabase schemas, and cleanup of stale documentation naming/config notes.

## 3. Application Architecture

The app follows a feature-sliced Flutter architecture:

| Layer | Path | Responsibility |
| --- | --- | --- |
| App entry | `lib/main.dart` | Bootstraps config, DI, lifecycle observer, and `GetMaterialApp` |
| Core | `lib/core/` | Config, dependency injection, routing, theme, local DB, sync, Supabase, Firebase, services |
| Features | `lib/features/` | Screens and controllers for auth, dashboard, transactions, analytics, budgets, rules, recurring, voice, settings |
| Shared | `lib/shared/` | Reusable widgets, transaction model, category visuals, currency formatting |
| Backend | `supabase/sql/` | Idempotent SQL setup for tables, policies, triggers, grants, indexes, cron |
| Tests | `test/` | Smoke test plus promo screenshot generation tests |

High-level flow:

```text
User action
  -> Feature screen
  -> GetX controller
  -> Drift local database
  -> Optional sync queue / Supabase write
  -> Reactive Drift stream updates UI
  -> Optional rules, notifications, analytics, Crashlytics
```

Important architectural choice: the cloud is not treated as the immediate source of truth for day-to-day UI. Local Drift streams are the primary UI driver, which keeps guest mode and offline usage viable.

## 4. Startup and Dependency Logic

Startup begins in `lib/main.dart`:

1. `WidgetsFlutterBinding.ensureInitialized()`.
2. `AppConfig.init()` loads runtime env data through `EnvConfigService`.
3. `DependencyInjection.init()` initializes services.
4. The app renders `SpendAnalyticsApp`, using light/dark themes and `AppRoutes.splash` as the initial route.
5. `_LifecycleObserver` watches app resume events and opens the biometric lock dialog when needed.

`DependencyInjection` is split into critical and non-critical phases:

| Phase | Services |
| --- | --- |
| Critical, awaited | `FirebaseBootstrapService`, `SupabaseService`, `CrashlyticsService`, `AnalyticsService`, `AppDatabase`, `ThemeService`, `AuthController`, `CategoryController`, `SettingsController` |
| Non-critical, unawaited | `LocalNotificationService`, `SyncManager`, `RealtimeService`, `RuleEngine`, `BiometricLockService` |

Each initialization step is wrapped in a timeout and logs failures instead of crashing startup.

Technical risk: because non-critical setup is started with `unawaited(_initNonCritical())`, a very fast route into transaction creation could request `SyncManager` or `RuleEngine` before those services are registered. The services are normally quick to register, but this is a startup race to watch if users can interact before non-critical initialization finishes.

## 8. Transaction Logic

Transactions are represented by `TransactionModel` with:

- `id`
- `userId`
- `amount`
- `type`
- `category`
- `paymentMode`
- `transactionDate`
- `updatedAt`
- optional `note`
- `tags`

Implemented transaction flows:

| Flow | Behavior |
| --- | --- |
| Add | Build `TransactionModel`, save locally, enqueue sync, evaluate rules, log analytics |
| Edit | Reuse existing id/user id, update local row, enqueue sync, log `transaction_updated` |
| Delete | Delete local row, enqueue cloud delete, log `transaction_deleted` |
| Local read | Screens derive state from Drift streams |
| Cloud write | `SyncManager` flushes queued transaction upserts/deletes when online and authenticated |

The add/edit form supports:

- Expense, income, and transfer types.
- Type-specific categories.
- Type-specific payment modes.
- Quick amounts.
- Date picker.
- Counterparty/merchant note composition.
- Transfer source/destination validation.
- Editing existing transaction arguments.

Important schema alignment issue:

- Local UI supports payment modes such as `wallet`, `bank_transfer`, and `cheque`.
- Supabase SQL currently allows only `cash`, `upi`, `card`, `netbanking`, and `other`.
- `SyncManager._normalizePaymentMode` maps unsupported modes to `other`, so richer local payment-mode details can be lost in the cloud copy.

## 9. Offline-First Sync and Conflict Resolution

Sync is handled by `lib/core/sync/sync_manager.dart`.

Outbound behavior:

1. Local transaction is saved first.
2. Transaction operation is enqueued as `upsert` or `delete`.
3. `SyncManager` checks connectivity and Supabase auth.
4. Up to 100 queue items are flushed in creation order.
5. Successful rows are deleted from the queue.
6. Failed rows increment `retryCount`, store `lastError`, and record to Crashlytics.

Inbound behavior:

- `pullAllFromCloud(userId)` fetches all remote transactions after sign-in.
- Fresh local installs accept remote rows.
- Existing devices use last-write-wins based on `updatedAt`.

Realtime behavior:

- `RealtimeService` subscribes to Postgres changes on `public.transactions` filtered by `user_id`.
- Inserts/updates merge into local Drift.
- Deletes compare remote commit timestamp against local `updatedAt`.
- If local wins, the local transaction is re-enqueued for cloud upsert.

Conflict model:

| Case | Outcome |
| --- | --- |
| Remote `updated_at` newer | Remote row replaces local |
| Local `updatedAt` newer | Local row is retained and re-enqueued |
| Equal timestamps | Local row wins |

Current sync scope:

- Transactions: queue-based local-first sync.
- Budgets: direct local/cloud reconciliation for current month.
- Rules: direct local/cloud reconciliation.
- Categories: local preferences only.
- Recurring expenses: Supabase schema exists, but app logic is placeholder.
- Notification events: local only.

## 10. Dashboard and Analytics Logic

Dashboard:

- Subscribes to local transactions for the active user.
- Computes monthly spend for the current calendar month.
- Hydrates first name from Supabase user metadata or email.
- Shows guest-mode state.
- Wraps dashboard content in `UpgradeAlert`.

Analytics:

- Supports ranges: `Week`, `Month`, `3 Months`, `Year`, `All`.
- Computes total spent, total income, net flow, previous-period expense delta.
- Builds trend buckets by day, week, or month depending on range.
- Builds category slices from expense totals.
- Computes top "merchants" from the first part of the note or fallback category.
- Produces simple insight copy based on top category movement.

Analytics are derived entirely from local transactions, so they work offline and in guest mode.

## 11. Budget Logic

Budget logic is implemented in `BudgetController`.

Current behavior:

- Active month/year are fixed to `DateTime.now()` at controller initialization.
- Default budgets are seeded if no budgets exist for the active month:
  - Food: `4000`
  - Transport: `2500`
  - Shopping: `3000`
- Local category spend is derived from expense transactions in the same month/year.
- Supabase-authenticated users sync active-month budgets:
  - Fetch cloud budgets into local.
  - Push local budgets back to Supabase.
- Budget upserts update local first, then call `SupabaseService.upsertBudget`.

Current limitations:

- No general budget sync queue; cloud writes are direct best-effort calls.
- Current controller is scoped to the current month; historical/month picker behavior is not part of the controller logic.
- Supabase budget uniqueness supports both `category_id` and `category_name`, while local budgets use category names.

## 12. Rules and Notification Logic

Rules are stored locally in `UserRules` and optionally synced to Supabase `user_rules`.

Rule UI/status:

| Rule type | UI/config status | Runtime evaluation |
| --- | --- | --- |
| `budget_threshold` | Supported | Implemented |
| `daily_limit` | Supported | Implemented |
| `no_entry_reminder` | Suggested/configurable | Not evaluated by `RuleEngine` |
| `category_spike` | Suggested/configurable | Not evaluated by `RuleEngine` |
| `weekend_overspend` | Suggested/configurable | Not evaluated by `RuleEngine` |
| `recurring_due` | Data model/title support | Filtered out from visible rules and not evaluated |

`RuleEngine.evaluate(txn)` only runs for expense transactions.

Implemented rule actions:

- Budget threshold:
  - Finds matching category budget for the transaction month.
  - Computes current and previous spend ratio.
  - Fires only when crossing the configured threshold.
  - Writes a local notification event and attempts to show a local notification.
- Daily limit:
  - Computes total daily expense.
  - Fires only when crossing the configured limit.
  - Writes a local notification event and attempts to show a local notification.

Notification center:

- `NotificationCenterController` watches local notification events for the active user and global/null-user events.
- Users can clear all local notification events for the active user.

Local notification service:

- Uses `flutter_local_notifications`.
- Encodes payload JSON.
- Navigates to payload `route` when notification is tapped.

## 18. Supabase Backend Status

SQL setup is in `supabase/sql/` and is applied by `supabase/scripts/run_all_sql.sh`.

Script order:

1. `00_extensions.sql`
2. `01_schema.sql`
3. `02_indexes.sql`
4. `03_triggers.sql`
5. `04_rls.sql`
6. `05_grants.sql`
7. `06_crons.sql`

Extensions:

- `pgcrypto`
- `pg_cron`
- `pg_net`

Tables:

| Table | Purpose |
| --- | --- |
| `user_profiles` | User profile, display data, currency, FCM token |
| `categories` | Cloud category records |
| `transactions` | Cloud transactions |
| `recurring_expenses` | Cloud recurring expense definitions |
| `budgets` | Cloud category/month/year budget limits |
| `user_rules` | Cloud user alert rules |
| `job_run_log` | Backend cron execution log |

Indexes:

- User/date and user/updated transaction indexes.
- Category and type transaction indexes.
- Active-only transaction partial index.
- Recurring active/due index.
- Budget user/month/year index.
- Active rule index.
- Job log index.

Triggers:

- Shared `public.set_updated_at()` trigger function.
- `updated_at` trigger installed for profiles, categories, transactions, recurring expenses, budgets, and user rules.

RLS:

- RLS is enabled for all public user-data tables.
- Policies use `to authenticated` plus `auth.uid()` ownership checks.
- `job_run_log` intentionally denies direct authenticated access.

Grants:

- Explicit Data API grants are present for `authenticated` and `service_role`.
- `job_run_log` access is limited to `service_role`.

Cron:

- `spendsense-clean-soft-deleted`: deletes soft-deleted transactions older than 90 days.
- `spendsense-roll-recurring-due-dates`: advances overdue active recurring expense due dates.

Backend/app mismatch:

- Supabase `transactions` has `is_deleted` and a cleanup cron, but app delete currently calls hard `.delete()` on `transactions`. The soft-delete cleanup path is not used by current app transaction deletion.
- Supabase recurring infrastructure exists, but app recurring logic is not connected.
- Supabase categories infrastructure exists, but app categories remain local preferences.

## 22. Current Technical Risks and Gaps

Priority risks:

| Risk | Impact | Suggested fix |
| --- | --- | --- |
| Payment-mode mismatch between local and Supabase | Cloud records lose detail for `wallet`, `bank_transfer`, `cheque`, and transfers | Expand Supabase `payment_mode` check constraint or normalize UI options to supported values |
| Non-critical DI race | Fast navigation can request services before registration | Register non-critical services synchronously before async init, or await critical-for-navigation services |
| Rules UI exceeds engine behavior | Users may believe suggested rules are active when they are not evaluated | Implement remaining rule evaluators or label them as coming soon |
| Recurring app layer is placeholder | Backend cron exists but no product workflow uses it | Add local recurring model/table/controller and sync path |
| Category cloud table unused | Custom categories do not roam across devices | Add category sync or remove backend category promises |
| Soft-delete cron unused by app delete | Backend cleanup job does not match app deletion behavior | Switch app delete to soft update or remove cron path |
| Empty app version in tests | Upgrader warning noise and possible production config issue if env missing | Provide safe fallback for `AppConfig.appVersionString` or avoid passing empty `minAppVersion` |
| Documentation drift | Setup and architecture docs can mislead future work | Update README/ARCHITECTURE/RELEASE_NOTES naming and service references |
| Promo tests mutate assets | Routine test runs dirty the worktree | Split screenshot generation into a separate command or make it opt-in |
